# التنسيق: Graph + Loop (نموذج هجين)

## لماذا هجين؟
- **Graph حتمي (DAG)** للمراحل الرئيسية = قابل للتكرار، التدقيق، الاستئناف، والبيع ("منظومة صناعية لا لعبة prompt").
- **Agent Loop** داخل عقد محددة فقط (تصميم/تقييم/إصلاح) حيث المرونة اللغوية ضرورية.

## الرسم البياني الرئيسي

```
load_spec ──► normalize ──► analyze ──► design_tools ──► generate_server
                                              ▲                │
                                              │(repair ≤3)     ▼
                                     repair ◄──────────── harden
                                          │                  │
                                          ▼                  ▼
                                       evaluate ────────► certify
```

## بنية العقدة (Node)

```ts
interface PipelineNode {
  /** معرف المرحلة */
  readonly stage: StageId;
  /** هل العقدة تستدعي LLM؟ (تحكم بالتكلفة والحتمية) */
  readonly kind: "deterministic" | "agent";
  /** التنفيذ: يستقبل السياق ويعيد حدثاً */
  run(ctx: PipelineContext): Promise<NodeOutcome>;
}
```

- `NodeOutcome` أحداثه: `completed | failed(retryable) | failed(fatal) | needs_repair`.
- كل عقدة **idempotent**: إعادة تنفيذها بنفس المدخلات تنتج نفس النتيجة (مفتاح idempotency = hash المدخلات).

## سياسة إعادة المحاولة

| نوع الفشل | السلوك |
| --- | --- |
| خطأ شبكة LLM / timeout | retry أسي 3 محاولات (1s, 4s, 16s) + jitter |
| خرج مخالف للمخطط | تحويل مباشر لوكيل الإصلاح (لا retry أعمى) |
| finding حرج في التحصين | فشل فوري fatal — لا إصلاح تلقائي يتجاوز سقف الدورات |
| سقف الإصلاح (3 دورات) | تعليق الحالة `needs_human` وإشعار |

## حلقة الوكيل الداخلية (Agent Loop داخل العقدة)

```
مهمة → [اختيار أداة] → [تنفيذ أداة] → [ملاحظة النتيجة] → هل اكتمل عقد المخرج؟
              ▲                                            │ نعم → مخرج Zod → بوابة الحقيقة
              └──────────────── لا (حد 8 خطوات) ◄──────────┘
```
- سقف 8 خطوات لكل نداء وكيل — بعدها فشل منظم.
- كل خطوة تُسجل كحدث في L1 (قابلية استئناف وتشريح).

## مطالب النظام والرسوم
- مطالب كل وكيل موحدة البنية (الدور/القيود/عقد المخرج — انظر `agents.md`) ومحفوظة كملفات TS مستقلة في `agents/src/prompts/` قابلة للمراجعة والتغيير دون لمس المنطق.
- درجة حرارة النموذج = 0.2 افتراضياً للتصميم، 0 للتقييم.

## الأحداث والاستئناف
- كل انتقال مرحلة = `PipelineEvent` يُلحق بـ stream في L1 ويُرحّل لسجل التدقيق.
- انهيار العملية في أي لحظة؟ الإقلاع يعيد قراءة آخر snapshot ويستأنف من آخر عقدة مكتملة (بفضل الـ idempotency).

## قرارات التنفيذ المثبتة
- **الترميز**: `packages/orchestrator` — `graph.ts` (العقد و`NodeOutcome` الأربعة) + `engine.ts` (المحرك، 189 سطراً) + `contracts.ts` (العقود الخارجية) + `context-store.ts` (snapshot موقعة SHA-256 تكشف أي عبث) + `event-log.ts` + `retry-policy.ts` + `nodes/` (الثماني + repair-node + probe-targets).
- **jitter حتمي**: ±10% مشتق من رقم المحاولة لا من عشوائية — نفس الفشل يعطي نفس الجدول دائماً.
- **خرائط الفشل**: `DESIGN_ROUNDS_EXHAUSTED` بعد إصلاح المصمم الذاتي = تصعيد بشري مباشر (لا retry أعمى). النتيجة الحرجة في harden = فشل فوري. الإصلاح بالترقيع محصور بـ harden وevaluate؛ فشل generate_server بنيوي = توقف (ترقيع الملفات لا يصلح تصاميم فاسدة).
- **الاستئناف**: `PipelineContext.toSnapshot()` بعد كل مرحلة مكتملة عبر `SnapshotStore` (واجهة جاهزة لطبقة الذاكرة)، و`withSuspensionAfter(stage)` يوفر إيقافاً متحكماً به لاختبار القبول والعروض. التحقق عند الاستئناف: شكل العقد + البصمة معاً.
- **أهداف الفحص الحي** تُشتق حتماً من التصاميم (أول أداة بمعامل مسار)؛ غياب مرشح صالح = رفض صريح للفحوص الحية لا تخطيها بصمت.
